## Notification and search research notes

The notification design will persist a domain change and its notification intent in the same school-database transaction. A worker consumes committed intents with idempotent recipient/channel delivery records. This addresses the save-success/send-failure gap described in [AWS's transactional outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html). Delivery remains retryable; provider acceptance and confirmed delivery are separate states. Sender channel choices cannot bypass recipient permissions, school configuration or user preferences. This is a design requirement, not an implemented delivery service.

Global search will query school content with current access restrictions before returning results. PostgreSQL's [text-search index guidance](https://www.postgresql.org/docs/18/textsearch-indexes.html) supports evaluating GIN-backed document search; Arabic tokenization, names, partial matches and representative query plans still need measured evaluation. Search snippets must come from authorized fields, and stale index entries must never retain revoked access. The current navigation launcher does not satisfy this requirement.

## Assignment workspace checkpoint

Assignments now have the lifecycle the domain document describes. A teacher designs an assignment on a full page: a rich-text brief through the shared Lexical editor, learning resources uploaded through the private file lifecycle, an audience of the whole class, saved class groups or named students, an availability instant, a due instant with a late policy (refused, accepted and marked, or accepted with a percentage deduction) and an optional close instant, a hand-in format (written, files or both) with attachment count and size limits, a resubmission policy and an optional rubric whose points must add up to the maximum score. Drafts are private to authors in scope; publishing is revision-checked and refuses an incomplete draft with the missing items named. A class audience follows the roster, so students enrolled later see the work; group and student audiences are fixed when saved, and anyone who has handed in keeps the assignment whatever happens to the audience afterwards. Published work can be archived; archived work stays readable.

Learners keep a revisioned draft (text and attachments) and hand in explicitly. Handing in cuts an immutable attempt; a retried submit carrying the same revision returns the attempt it already created. The window (not yet open, open, late, closed) and the resubmission policy are enforced in the API, late attempts are flagged, and a deduction policy is applied to the released score while the raw score stays visible. Assessments belong to an attempt, take rubric points and comments or a direct score plus rich-text feedback, and stay private until released; releasing mirrors the result onto the submission so lists and the family read it without joining attempts. The legacy quick-create, plain-text submit and quick-grade endpoints run on the same model.

Private files: a client declares a file (purpose, name, media type, size) and receives a server-generated destination; bytes stream to the API, which verifies the size, records the SHA-256 and only then marks the file ready. Executables and SVG are refused, names are sanitised, downloads carry an attachment disposition with an ASCII fallback and a UTF-8 form for Arabic names, and every download is authorised by the assignment or submission that links the file rather than by the id. The web forwards uploads and downloads with the session cookie and never holds a token or a path. Storage is a per-school directory tree behind a store interface; an object-store adapter and abandoned-upload clean-up remain open.

One canonical record, `/assignments/{id}`, serves every role. Teachers get the brief, the schedule and settings, a learners table with each student's state (not yet open, not started, draft, submitted, returned, missing, with a late marker) and a review tab with attempt history and the assessment form; students get the brief and their own work with the editor, attempt history and released feedback; parents get the same read-only for the selected child. ## Notification module checkpoint

Notifications are a transactional outbox in each school database. Publishing an assignment, releasing an assessment, sending a message or reply, publishing an announcement and publishing a newsletter edition write the event, one in-app notification per recipient and one delivery row per channel in the same transaction as the change. Recipients come from relationships: an assignment reaches its learners and their guardians, a released result the student and their guardians, a message its addressees, an announcement or newsletter the roles in its audience; a parent only hears about their own child. Per-person preferences hold the email and SMS switches, the language for those channels and muted types; a disabled channel, a muted type or a missing address produces a recorded skip, not silence. A worker inside the API polls each school, claims pending rows with row locks, renders server-side English or Arabic templates, calls the configured HTTP provider adapter and records receipts, failures and the next attempt with a growing backoff that stops after five tries. Without a configured provider, email and SMS are recorded as skipped for that reason, and administrators read every attempt in the notification log.

The web shows a bell with the unread count, a dropdown of recent notifications that opens the record each one is about, a full list with mark-all-read and an unread filter, and a preferences page. Announcements are written in the shared editor with an audience, published once and read on their own page, with a News entry in every role's navigation; newsletter drafts now publish into immutable editions with their own reader page, and the newsletters list opens editions in the app and older external files in a new tab. Accounts gained a mobile number for SMS.

The browser run found two mobile defects: the preferences toggles used the vertical field layout, which gives every child full width, and the shared page header kept its action group from shrinking, so three actions overflowed a 390px viewport. Toggles now use the registry's horizontal field with its content slot, and the header's action group wraps instead; sixteen pages across the four roles were re-probed at 390px in both locales with no overflow. The first delivery retry is a minute in production, so the suite sets a one-second retry base through the new environment setting rather than waiting.

Running the notification regression in three browsers at once exposed assumptions the single-browser run hid: the spec had renamed a seeded teacher to exercise retries and broke every other sign-in, it read only the first page of the log, and it looked rows up by type where parallel runs produce several. It now creates its own retry account, the log gained a search over recipient, address and title that the administrator page also uses, and the memory provider fails once per message rather than per address.
