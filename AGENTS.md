# Farida LMS agent guidance

The platform is Farida LMS. A school name is never the platform name.
The repository is a Bun workspace with independently deployable web and API apps.
Use `bun run ready` for final verification. End-to-end tests create isolated
school databases; never reset the developer's school to make a test pass.

Working notes for AI coding agents (and humans in a hurry).

Most of what follows is not style preference — it is a list of traps this codebase
has already fallen into. Each rule exists because breaking it produced a real bug.

---

## Commands

| Do this                  | Not this                                                            |
| ------------------------ | ------------------------------------------------------------------- |
| `bun run test`           | `bun test` — Bun's own runner. Ignores `vitest.config.ts` entirely. |
| `bun run build`          | `bun build` — Bun's own bundler. Not the app build.                 |
| `bunx shadcn@latest ...` | `npx`                                                               |

```sh
bun install          # also compiles i18n and bootstraps .env
bun run db:up        # Postgres 18 in Docker, port 5433
bun run db:reset     # provision roles, recreate the cell, migrate, seed
bun run dev          # :3000
bun run lint         # oxlint (type-aware) + message-catalogue parity
bun run format:write # oxfmt
bun run type-check   # tsc --noEmit
bun run test         # vitest
bun run test:api     # the API against a throwaway cell and directory (Bun's runner)
bun run test:ops     # the console's business stores against throwaway databases
bun run test:e2e     # playwright, builds and serves the production bundles
```

`apps/media` is Rust and outside `bun run ready`. After changing it, run
`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and
`cargo test` there; the tests encode a clip and draw a PDF's page, so they
need `ffmpeg` and poppler's `pdftoppm` on the path. CI's `media` job runs
the same three.

**Bun 1.4.4 is pinned** in packageManager, Dockerfile and `.github/setup/action.yml`.
Keep all three aligned; Bun 1.3 cannot read this lockfile version.

**The app runs on Bun, the test tooling runs on Node.** `drizzle-orm/bun-sql`
imports the `bun` module, and Vite executes SSR in its own process, so `dev`,
`build`, `preview` and `start` all pass `--bun`. Drop that flag and every page
fails with `Cannot find package 'bun' imported from .../bun-sql/mysql/driver.js`,
which is a resolution error, not a missing dependency: the `drizzle-orm/bun-sql`
barrel eagerly imports the MySQL, Postgres and SQLite drivers, and all three
require Bun.

vitest and playwright keep their `#!/usr/bin/env node` shebangs. That is why
**nothing under `apps/web/src/utils/` may import `~/db`** — one such import makes a test
file unloadable. Anything worth unit testing goes in `apps/web/src/utils/school.ts`,
which is pure by construction.

## Never edit these

| Path                                       | Why                                                                                |
| ------------------------------------------ | ---------------------------------------------------------------------------------- |
| `apps/web/src/routeTree.gen.ts`            | Generated by the TanStack Start plugin on dev/build.                               |
| `apps/web/src/i18n/**`                     | Generated by Paraglide from `messages/*.json`.                                     |
| `packages/ui/src/*.tsx`                    | Vendored shadcn registry code. `shadcn add` overwrites it.                         |
| `packages/database/migrations/*/*_tables/` | Generated from the table declarations. Change those and run `bun run db:baseline`. |
| `apps/api/src/pictures/pictures.json`      | Open picture index. Rebuild with `bun scripts/picture-index.ts`.                   |

To change a `ui/` component, prefer a wrapper you own. If you truly must fork one,
say so in the PR — the next `shadcn add` will silently revert you.

`packages/ui/src/system/` is ours: the design system's components, shared by
the portal and the console. Build every screen from them, extend them there
when a screen needs more, and give each a named props interface and a spec.
`db:verify` refuses a component in either app or the system that types its
props inline, or whose doc comment sits above its props interface instead
of above the component.
`docs/design-system.md` maps each of its rules to the module that implements
it.

A record page (a customer, a school, a lead) follows the anatomy in that
document's Record page section: header, figures, a To do list, then tabs,
About first and History last, each tab one thing designed for its content
(a table with its own action and empty state, or titled summary lists). No
supporting column beside tabs, no tab grouping unrelated things, no "No X
yet" under a heading. The console's pages are designed in `docs/console.md`;
change a page's design there before changing its code, and check it against
that document's review list.

Adding a route? Run `bun run dev` once so the plugin regenerates the route tree,
otherwise `tsc` will not know the route exists.

## UI: Base UI, not Radix

shadcn made Base UI the default. The package is **`@base-ui/react`** (not
`@base-ui-components/react`, which was abandoned at RC). Radix is gone from this repo.

- `asChild` does not exist. Use **`render`**: `<Trigger render={<Button />} />`.
- **`Menu.GroupLabel` must live inside a `Menu.Group`.** A bare `DropdownMenuLabel`
  throws `MenuGroupContext is missing` and takes the whole page down via the error
  boundary. Radix allowed it; Base UI does not.
- Style hooks are `data-open:` / `data-closed:` / `data-checked:`, not
  `data-[state=open]:`. The variants come from `@import "shadcn/tailwind.css"` — do
  not remove that import.
- `Select`'s `onValueChange` gives you `string | null`, not `string`.
- Prefer controlled inputs (`value` + `onChange`). An uncontrolled Base UI `Input`
  outside a `Field` does not reliably fire `onChange`.

`form.tsx` is retired upstream. **Forms are `Field` + `FieldGroup` +
`@tanstack/react-form`.** Valibot schemas plug straight into `validators` via
Standard Schema — there is no resolver package.

## Localisation is not optional

Every user-visible string lives in `messages/en.json` **and** `messages/ar.json`.
`bun run lint` fails if they drift (`scripts/check-i18n.ts`), because inlang removed
its own `lint` command with no replacement.

```tsx
import * as m from "~/i18n/messages";
m.membersTitle(); // yes
<h1>Members</h1>; // no
```

**Arabic is RTL, so use logical properties only**: `ps-*`/`pe-*`, `ms-*`/`me-*`,
`start-*`/`end-*`, `text-start`/`text-end`. Never `pl-*`, `ml-*`, `left-*`,
`text-left`. `components.json` sets `"rtl": true` so `shadcn add` stays logical too.

Locale resolves cookie → `Accept-Language` → `baseLocale`. `setLocale()` writes the
cookie and reloads, so the next document is _server-rendered_ in the new locale.

## API, sessions and school isolation

Read [docs/architecture.md](docs/architecture.md) before changing API contracts,
authorisation, school isolation or database ownership.

- `apps/api/src/systems/` owns business operations. The procedures in
  `apps/api/src/core/procedure.ts` resolve the session, the school and a unit of
  work before entering a handler.
- Capabilities are checked with `requireCapability` and `can` from
  `apps/api/src/core/procedure.ts`; which records a viewer reaches is decided
  only through `apps/api/src/core/reach.ts`, whose named scopes (`SCHOOL_WIDE`)
  say which capabilities open the whole school for each kind of work. A
  capability alone does not authorise a submitted student or class ID. Which
  guardians the school may follow, contact, notify or call is the families
  module's `app.guardian_permits`, and staff are the roles `app.staff_roles` names;
  `scripts/check-sources.ts` refuses a copy of either, or a `schoolWide` set
  outside `core/reach.ts`.
- Every API namespace belongs to core (`CORE_SYSTEMS`) or to one module in
  `packages/domain/src/modules.ts`, and a module's procedures answer
  `NOT_FOUND` at a school that does not have it, through the router. How
  modules are built and kept apart is "Modules" below; read it before
  touching anything a module owns.
- Every store in `packages/database/src/stores/` receives its transaction
  explicitly. Never introduce a process-global current school or current user.
- `apps/web/src/server/` contains HTTP bridges and cookie handling only. Web
  runtime code never imports database implementations.
- The QueryClient is constructed per SSR request. Never make it a server singleton.
- Server-function files must not use the `*.server.ts` filename pattern. TanStack
  import protection rejects that pattern even for legitimate RPC bridges.
- Use ORPCError in the API; throw Error rather than plain objects. Keep tokens,
  connection strings and full user profiles out of router `beforeLoad` context.
- Required API environment variables belong in `apps/api/src/env.ts`; required
  web variables also need validation in `apps/web/src/server/preflight.ts`.
- Use `import.meta.env.PROD` for build-time decisions. Runtime environment
  defaults do not describe the Vite build and once shipped devtools into SSR.
- Pure business rules and schemas live in `packages/domain/src/`. Node-based
  unit tests must not transitively import Bun SQL.

## Modules

The product serves schools, coding schools, course academies and
video-course schools, and there is no school type: every difference
between them is a module that is on or off. Core is what every school
has: people, sign-in, roles and access roles, courses, classes (each with
its own dates, `runs`), enrolments, students (anyone holding the student
role) and their leaving (`core.student_departures`), school days, messages,
announcements, the calendar, documents, files, media, consents, privacy,
search and billing. Core is enough to teach. Years, grades, homerooms,
guardians and periods are modules (`school_years`, `grade_levels`,
`homerooms`, `families`, `timetable`), as are coursework, attendance and
e-learning. `docs/plans/modular-core.md` is the design and why.

`MODULES` in `packages/domain/src/modules.ts` gives each module what it
`requires` (alternative groups: `standards` needs coursework or
e-learning), whether Basic includes it, whether the school switches it on
itself, the API namespaces it owns and the words it owns (capabilities,
notices, search and template kinds, calendar categories, setup steps). A
module is on where the plan includes it, what it requires is on, and the
school switched it on if it switches.

**Core names no module, in code or in SQL.** Where core or a module needs
what another knows, the consumer declares a typed point next to itself and
the module that knows contributes to it from its own files:

- API: `point<T>(name)`, `contribute` and `contributionsTo` in
  `apps/api/src/core/extension.ts`. Every module's `ModuleContributions` is
  listed in the composition root, `apps/api/src/extensions.ts`, and a point
  yields only those of the modules on at the school. `everyContribution`
  reads past the school's modules, and only for a point listed in
  `EVERY_MODULE` with its reason (retention, record joins, file sweeps).
- Workers: a module's background job is a `ModuleWorker`
  (`apps/api/src/core/workers.ts`) listed in `MODULE_WORKERS`, and acts
  only for schools where its module and its `needs` are on
  (`schoolsWith`, `workerScope`). A worker with no request reads points
  through that scope, as a request does.
- Web: `slot<T>(name)`, `fill`, `useSlot` and `filled` in
  `apps/web/src/utils/extension.ts`; every module's `ModuleFillings` is
  listed in `apps/web/src/extensions.ts`. `everyFilling` is only for a page
  before sign-in and for the switch that turns a module on.
- Pages: core's are `CORE_PAGES` in `apps/web/src/utils/pages.ts`; a
  module declares its own by filling `modulePages`, and the navigation
  (`navItems`), the route guard and `apps/web/src/utils/pages.spec.ts` all
  read that, so a page and its link cannot disagree.
- Who acts for a learner: core asks `apps/api/src/people/acting.ts`
  (`actorsFor`, `answerersFor`, `hearersFor`, `decidesFor`) and the
  families module answers through the `actingFor` point. Without it, or
  without a guardian, a learner of the school's deciding age
  (`orgs.learners_decide_from`, 18 by default, set in Settings), or any
  learner of a school that states its learners are adults
  (`orgs.learners_are_adults`), answers for themself, and one who does
  not decide still hears the school's notices.
- Before sign-in the portal knows only `identity.portalFace`: its
  `audiences` (who besides students and staff signs in, such as families)
  and `doors` (public pages such as `apply` and `badge`), each contributed
  by its module. Its colour is core's `orgs.brand_colour`, set in Settings,
  else the colour a module lends through `portalLooks` (the website's main
  colour) in its nearest readable shade (`portalColour` in
  `packages/domain/src/brand.ts`), else the platform's. The website's theme
  follows the brand colour unless the builder sets its own (`siteThemeFor`
  in `packages/domain/src/site-brand.ts`).
- Whether a class or a learner is young: everything asks
  `youngClassesOf` (`apps/api/src/classes/points.ts`) or
  `youngStudentsOf` (`apps/api/src/people/points.ts`), never a grade. The
  early years module answers from the classes marked young
  (`core.young_classes`), and with grade levels from the young grades
  through its link `apps/api/src/early-years/grades.ts`.

**What two modules do together lives in a link file.** A module that adds
to a point or slot of a module it does not require, or owns a table that
names one, does so from a file listed in `LINK_FILES`
(`scripts/module-files.ts`) with its owner and `needs`. Its contributions
declare the same `needs`, so they run only where the owner and every need
are on. Only the composition roots import it, and the owner's other link
files with the same needs. A link table is owned
the same way in `TABLE_OWNERS`; it has rows only where both are on. An API
namespace that needs a second module is in `LINK_SYSTEMS`.

**The database cannot tell whether a module is on**, since entitlements
live in the directory. A module's rule that must stop when it is off runs
in its stores, called from its API; a trigger or key holds only what is
true either way. An off module is dormant: its rows stay, and nothing of it
refuses what core does. A module keeps what it mirrors from core tied by a
key where it can (a homeroom place is a cascading key to its enrolment) and
writes again what it derives into core when it next acts.

**Wording.** A sentence that names a module's concept (a year, a grade, a
guardian, a period) is never shown by core. Core shows the neutral
sentence, `fooCore` in `messages/*.json`, through `useWords()`
(`apps/web/src/utils/words.ts`): `words(m.fooCore)()`. The module puts its
own back from its contributions with `replaceWords(m.fooCore, m.foo)`; a
sentence that speaks of a second module names it in `alsoNeeds` or lives in
a link file. A module words the emails and texts of its own notices
through the `noticeLines` point (`apps/api/src/notifications/points.ts`).

### The gates

None has an exception list; any reach across an owner fails the build.

- `bun run db:verify` runs the ownership gate (`scripts/check-rls.ts`,
  `packages/database/src/ownership-gate.ts`). Every table belongs to core
  or one module in `TABLE_OWNERS` (`packages/database/src/ownership.ts`),
  with `needs` for a link table; every descriptor namespace in
  `NAMESPACE_OWNERS`; every column that names a module's concept without a
  key (`school_year_id`, `homeroom_class_id`, `class_period_id`,
  `relationship_id`) in `COLUMN_OWNERS`. A key, a namespace column or a
  concept column may reach core, its table's owner, what that owner
  requires in every alternative, and its `needs` (`mayReach` in
  `packages/domain/src/ownership.ts`); a core table reaches core alone. A
  table or namespace with no owner, or an owner for something that does
  not exist, fails too.
- The source checks (`scripts/check-sources.ts`, rules in
  `scripts/module-files.ts`) hold the code to the same owners. A module's
  files (`MODULE_FILES`) are imported only by the module, a module that
  requires it in every alternative, a link file that needs it and
  `COMPOSITION_ROOTS`. A web file asks `modules.<id>` only of a module it
  may import; otherwise it reads a slot the module fills. Only the files in
  `MODULE_CATALOGUES` (the plan's features card) list every module. SQL
  names a table or function of a module in `SQL_CARVED` only from a file
  that may import it, or from a registry in `SQL_READERS`, each with its
  reason. A migration function (`FUNCTION_OWNERS`) names only tables its
  owner may reach.
- `apps/api/test/router.test.ts` refuses a namespace owned by neither core
  nor a module, and `apps/web/src/utils/pages.spec.ts` a route owned by
  neither, or by both.
- Browser specs walk schools without modules: `e2e/core-school.spec.ts`
  (the seeded academy, from setup to a register, an assignment, a lesson
  and a message), `e2e/module-surfaces.spec.ts` and
  `e2e/module-pages.spec.ts` (no word of an off module, in English and
  Arabic, using `e2e/fixtures/module-words.ts`), and
  `e2e/self-learner.spec.ts`, `e2e/yearless-teaching.spec.ts`,
  `e2e/plain-classes.spec.ts`, `e2e/core-classes.spec.ts`,
  `e2e/module-gates.spec.ts`.

### Adding to them

A module:

1. Add its id to `MODULE_IDS` after every module it requires, and its
   `ModuleSpec` to `MODULES`. Type-check then asks for its name in the
   console (`apps/ops/src/format.ts`) and on the plan's features card.
2. Declare its tables in `packages/database/src/tables/`, list them in
   `tables/index.ts`, give each an owner in `TABLE_OWNERS`, its concept
   columns and namespaces in `COLUMN_OWNERS` and `NAMESPACE_OWNERS`, and
   each table that keys a person an erasure rule. Run
   `bun run db:baseline` (see "The database").
3. Put its API in `apps/api/src/<module>/` and `apps/api/src/systems/`,
   with the namespaces in its `systems`; its contributions in
   `apps/api/src/<module>/contributions.ts`, listed in
   `apps/api/src/extensions.ts`; a worker in `MODULE_WORKERS`.
4. Put its web files in `apps/web/src/components/<module>/` with its
   fillings (pages, links, tabs, Today cards, setup steps, words) in
   `contributions.tsx`, listed in `apps/web/src/extensions.ts`.
5. List its files in `MODULE_FILES`, and the module in `SQL_CARVED` once
   no other file names its tables in SQL.
6. Seed it, and add a browser spec of a school with it on and one with it
   off.

A link between two modules that do not require each other: put the code
in a file of the owner named for the other (`apps/api/src/admissions/years.ts`),
list it in `LINK_FILES` with `owner` and `needs`, give its contributions
or fillings the same `needs`, and list it in the composition root. A link
table is a table of its own with `{ owner, needs }` in `TABLE_OWNERS`,
never a nullable column on either side.

A point or a slot: declare it beside the code that reads it, named for what
that code needs, typed with what a contribution gives; read it with
`contributionsTo` or `useSlot`. Add none that nothing reads.

A sentence that names a module's concept: add the neutral `fooCore` and the
module's `foo` to both catalogues, show `words(m.fooCore)()` in core, and
add `replaceWords(m.fooCore, m.foo)` to the module's fillings.

## What this product must not do again

Each of these is a defect found in the school portal this product was first
built to replace. A reviewer checks for them.

**Say "not recorded", never render a blank.** Any value that can legitimately
be absent goes through `<Value>`. The old portal printed a label and then
nothing, so a parent could not tell a missing birthdate from a broken page.

**Never print a raw counter.** It leaked server variables into the markup
(`53`, `58 1 0 0`). Every number on screen carries a label.

**No dead links.** A third of its navigation 404'd, on every page. A route that
is not built does not go in `navigation.ts`, and `e2e/access.spec.ts` walks
every nav link for every role to keep it that way.

**Every table needs a mobile layout**, either a card list below `sm:` or a
scrollable region with a caption. Nothing in the old portal was responsive.

**The heading must match what is displayed.** Its calendar was titled
"CALENDAR 2025 / 2026" while showing September 2026.

## One document model, no special fields

Every piece of content a person writes (announcements, assignments,
lessons, consent forms, pages) is one editor document (`packages/editor`,
`ContentDocument`). This is the rule the whole product is built on; a reviewer
rejects anything that works around it.

- **What is part of the content is a block, never a field beside the
  editor.** Pictures in the text, files, video, embeds, questions and
  attachments are editor blocks. Do not mirror them outside the document: no
  attachments list under the brief, no panel listing the document's
  pictures, no second place to edit them.
- **What belongs to a block is set on the block**, from the editor's one
  floating bar (`plugins/SelectionToolbar.tsx`): alt text, caption, size, who
  a photo shows. A host app adds such an action through `EditorMedia` in
  `packages/editor/src/context.tsx`, never with its own panel.
- **Settings about a document are not content.** A post's cover picture,
  summary, audience, dates, language, visibility and address describe the
  document for cards, lists and delivery; they belong in the details panel.
  A setting that is a picture gets the same picture actions as a block (who
  it shows) on its own control.
- **Anything another surface needs from the words is derived from them.** A
  reader's file list is the document's file blocks; a card without a cover
  shows the first picture. Computing it is fine; asking the author to enter
  content again is not.
- **No surface is special.** Before adding a control for one kind of document
  (an announcement, a page, a lesson), ask whether every document needs it. If it does,
  it is an editor capability; if it does not, it is a setting of that
  document.

## Routes

Routes are grouped by the session's context, its workspace: staff pages live
at the root under the pathless `apps/web/src/routes/_app/_staff/` layout
(`/today`, `/classes`, `/settings`), a family's under `_app/family/`, a
student's under `_app/me/`, and pages every context opens (calendar,
announcements) directly under `_app/`. `_app.tsx` gates authentication and
renders the shell; `_app/_staff.tsx`, `_app/family.tsx` and `_app/me.tsx` gate
the context. Both are required, because the server authorises data but only
the route can stop a page rendering at all.

Inside the staff workspace capabilities decide everything, never the
profile: an administrator who teaches and a teacher who holds an office
capability see the same pages as anyone else holding them. Every staff page
calls `requirePage` from `apps/web/src/utils/page-access.ts` in its loader
with the capabilities its API asks for, never its own check, and its item in
`apps/web/src/components/app/navigation.ts` is gated by the same ones. A page
with a personal and a school-wide side (classes, attendance, timetable,
today) shows both as tabs, the personal one first for whoever teaches.
`/admin/*` and `/teach/*` are the old staff areas and only redirect
(`apps/web/src/utils/moved-addresses.ts`).

Filters, the selected child, the selected week and the open folder all live in
the URL via `validateSearch`. None of them belong in `useState`. Read data with
`useSuspenseQuery` behind a route loader, never `useQuery` plus a loading
branch.

## The database

One Postgres 18 database per regional cell holds every tenant's rows; a
separate `directory` database maps a school slug or host to its tenant and
cell. The full contract is `docs/systems/platform-foundation.md` (conventions
in section 4, access profiles in 5, the request contract in 7, the gates in 8,
migration rules in 9). `bun run db:up` starts Postgres in Docker on port
**5433**, not 5432, so it cannot collide with a local server.

- **Tables** are Drizzle v1 declarations in `packages/database/src/tables/`,
  with `conventions.ts` holding the base columns, Postgres-style constraint
  names and the policy builders of each access profile. Partitioned tables and
  the search index are declared in `partitioned.ts`, which
  `packages/database/drizzle.config.ts` does not read, because drizzle-kit cannot create them.
- **Migrations** live in `packages/database/migrations/`, one folder per
  database: `cell/` (tenant data), `directory/` (the global routing of schools
  and hosts) and `business/`. Each holds one baseline, written as if the
  schema were designed today: a `tables` migration that drizzle-kit generates
  from the declarations, and hand-written migrations by topic for what
  drizzle-kit cannot express. The cell's migrations run in this order:
  `schemas` (schemas, extensions, the collation and schema grants),
  `functions`, `tables`, `keys` (`EXCLUDE`, `PERIOD` and `WITHOUT OVERLAPS`
  keys, deferrable keys, `NULLS NOT DISTINCT` indexes, column compression),
  `partitions` (partitioned tables, their policies and registry rows),
  `search` (the search index), `views`, `triggers` and `access` (forced RLS
  and every grant). The directory and business databases have `tables` and
  `access`. Each object appears once, in its final form.
- **No release has carried the baseline yet, so a change still rewrites it
  in place and appends nothing.** Change the declarations and run
  `bun run db:baseline`, which writes the `tables` migrations again from
  empty and keeps every topic migration's words and place, then edit by
  hand the topic migration the change belongs to. Do not run `db:generate`
  meanwhile, since it appends; the one use left is
  `bun run db:generate --custom --name <topic>` for a new topic, which
  `db:baseline` then keeps in its place. A database built from an earlier
  baseline cannot migrate to a rewritten one: `bun run db:reset` makes the
  developer's databases again. The release that carries the baseline
  recreates production. From then on an applied migration is never edited
  and changes are appended: generated ones by `bun run db:generate`,
  `db:generate:directory` and `db:generate:business`, hand-written ones by
  `bun run db:generate --custom --name <topic>` right after the generated one
  they complete.
- Never `drizzle-kit push`: it would drop what it does not understand.
  `scripts/db.ts` applies migrations as `migrator` with `SET ROLE
  cell_owner`, all pending ones in one transaction.
- **Roles are cluster objects** created by `packages/database/src/provision.ts`,
  not by migrations. The API connects as `app`, which is not the owner, has no
  `BYPASSRLS` and cannot delete. Every tenant table has a restrictive
  `tenant_isolation` policy and forced RLS.
- **Every query runs in a unit of work** (`packages/database/src/context.ts`):
  one transaction that binds the tenant with `app.begin_unit`. Only that module
  opens pools or calls `set_config`; `app.tenant_id()` raises when the tenant
  is not bound to the current transaction. Special-category tables (health,
  demographics, custody) are invisible until `withPurpose` sets their purpose.
- `bun run db:reset` provisions the roles, recreates `CELL_DATABASE`,
  `DIRECTORY_DATABASE` and `BUSINESS_DATABASE`, migrates and seeds five
  schools, and prints the logins: a school group of two schools (Northwind,
  `northwind` and `northwind-east`), a standalone school (`acme`), a school
  on Basic alone (`fernhill`), and Lanternfield Code Academy
  (`lanternfield`), adults on coursework, the gradebook, attendance and
  e-learning with no years, grades, homerooms, families or timetable. Northwind and Acme are
  entitled to every module. Every seeded account's password is
  `SEED_PASSWORD` (`packages/database/src/seed.ts`); the academy's are
  `admin.lanternfield@lanternfield.example.com`,
  `teacher1.lanternfield@...` to `teacher3`, and `student1.lanternfield@...`
  to `student12`. The business database (customers, contracts, invoices,
  operators) is the operator console's alone, as `business_admin`; no cell
  connects to it. Its schema is `packages/database/src/business/schema.ts`.
  `bun run db:verify` builds a cell
  from an empty database, fails if `drizzle-kit generate` would write a file,
  and runs the catalogue check (`scripts/check-rls.ts`), the source checks
  (`scripts/check-sources.ts`) and the isolation and behaviour suites
  (`bun run test:db`, Bun's runner against a throwaway database).
- `drizzle-kit` needs the Bun driver, so its commands run under `bun --bun`.
  Postgres 18 keeps its cluster in a versioned subdirectory, so `compose.yaml`
  mounts `/var/lib/postgresql` rather than `/var/lib/postgresql/data`.

Schema decisions worth not undoing:

- **Read state is per person**, never a column on the shared row, or whoever
  opens a school-wide notice first marks it read for everybody.
- **`users.birth_date` is nullable on purpose.** Schools genuinely lack some,
  and the interface says "not recorded" through `<Value>`.
- **Fixed vocabularies are `text` with a `CHECK`**, which one migration can
  change; school-configurable ones are descriptors with a fixed
  `system_meaning`, so behaviour never depends on a code a school typed.
- **Rows are tombstoned, not deleted** (`status = 'tobedeleted'`), and every
  update names the `version` it read.
- **Every table that names a person declares its erasure rule** in
  `packages/database/src/erasure-rules.ts`: erased by a retention policy,
  kept as a school record, or erasure still to build. `db:verify` refuses a
  table with a key to `core.users` that has none.
- **Every table belongs to core or one module** in
  `packages/database/src/ownership.ts`, and `db:verify` refuses any reach
  its owner may not make, with no exceptions (see "Modules", "The gates").
  A relation between two modules is a link table, never a nullable column.

## Lint and types

- **oxlint + oxfmt.** There is no ESLint and no Prettier. `eslint-disable` comments do
  nothing; do not add them. If a rule is genuinely wrong, scope it in `.oxlintrc.json`
  with a comment explaining why.
- `noUncheckedIndexedAccess` is **on**. `array[i]` is `T | undefined`. Handle it —
  don't cast it away.
- Type-aware lint is on (`oxlint --type-aware`), so `no-floating-promises` is enforced.
  `void` a promise only when you genuinely mean to ignore it.

## Before you claim it works

`bun run type-check` passing is not evidence that a feature works. The things that
actually break here — SSR, sessions, locale, hydration — are invisible to `tsc`.

Run `bun run test:e2e`. It builds and serves the **production** bundle across
Chromium, Firefox and WebKit, and the operator console as the `console`
project, signing operators in through a stand-in OpenID Connect provider
(`scripts/e2e-oidc.ts`). Each run makes its own databases and takes ports
3200-3210; a second run side by side (another worktree) sets its own block
with `E2E_PORT_BASE`, such as `E2E_PORT_BASE=3300`. Every one of the
following was caught there and by nothing else:

- a `Secure` session cookie that made sign-in silently impossible in Safari,
- devtools crashing SSR in production,
- two controls sharing one accessible name.
